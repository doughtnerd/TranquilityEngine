# Spike B0 for ADR 0352: plugin glue, fuel, worklet compile, fault isolation

- **Record:** [0352](../../../decisions/0352-third-party-audio-effects-are-sandboxed-wasm-modules-the-core-calls-inside-its-chains.md) (not edited; amendments proposed at the end)
- **Date:** 2026-11-22
- **Code:** `spikes/fx-plugin/` (its own Cargo workspace, not a member of `native/audio`) and
  `tools/spikes/fx-plugin/`
- **Raw results:** `tools/spikes/fx-plugin/results/b0.json` (the run quoted below; `b0.txt` is its summary),
  `fuel-a.json` and `fuel-b.json` (two extra Node runs of the fuel test, used to check it repeats)

## Summary

| Question | Answer (V8 only, see Blockers) |
|---|---|
| Glue cost per plugin call | **≈ 0.2 µs** once the output scan runs in a small trusted SIMD wasm helper. Naive JS loops cost **≈ 1 µs**, so the record's "well under 1 µs" holds only with that change. 32 instances cost 7–8 µs per quantum, about 0.3% of a 2.9 ms quantum |
| Fuel overhead | **0–30%** on real kernels (biquad cascade ≈ 0%, delay ≤ 8%, a trivial gain loop 11–30%) when the check is **branch-free** (a load from `fuel >> 31`). The record's `if … unreachable` form costs **+157%** on the tremolo in Node's V8 12.4, even when it checks only at loop headers. Chromium 153 doesn't have this cliff |
| Compiling in the worklet | Sync `new WebAssembly.Module` is allowed in `AudioWorkletGlobalScope` at any size (9 MB: 18 ms; the main thread refuses anything over 8 MB). Async `WebAssembly.compile` works there too. **A compiled `WebAssembly.Module` can't be posted over the node's port**: the worklet gets `messageerror`. It does arrive through `processorOptions` |
| Fault isolation | Traps, fuel exhaustion, NaN, out-of-range samples and `memory.grow` in `process` are all caught. The host's state ends **bit-identical** to a clean run in every case and every engine run. Recovery takes 35–160 µs for a module re-instantiation with 5 instances, and 2.5–10 µs to reset one instance |
| Architecture | **Holds.** No blocker found in V8. JavaScriptCore and SpiderMonkey are still unmeasured |

## Machine and engines

- Cloud VM: Intel Xeon @ 2.10 GHz, **4 cores**, 15 GB RAM. `uptime` read 12 h 29 min up, with load averages of
  1.3–2.9 at the start of the runs and 6.0 at the end: other agents shared the machine. Single runs; medians over
  5–9 trials, so treat differences under ~15% as noise unless a test repeats them.
- **Node** v22.23.5, V8 12.4.254.21-node.57.
- **Chromium** 153.0.8010.12 (Chrome for Testing, headless) through Playwright 1.64.1. The installed browser build is
  chromium-1243 while Playwright 1.64.1 expects 1248, so `run.mjs` falls back to the installed executable. Pages were
  served from memory on `E2E_PORT=4391`. The page runs every test on the main thread and again inside an
  `AudioWorkletProcessor` (a real `AudioContext` at 44.1 kHz with no audio device, autoplay allowed).
- **WebKit, Firefox: not run** (see Blockers).

## What was built

- **Test plugin** (`plugin/src/lib.rs`, 5.4 KB wasm, `no_std`, **no imports**): a draft of the ABI 1.0 exports
  (`myco_fx_abi`, `create`, `destroy`, `reset`, `io`, `process`, `tail_frames`, and its own `memory` capped at 4 MB).
  `process` works in place on planar stereo with 128 frames, with `p0` and `p1` of 16 parameters each. It has these
  kinds:
  - `null`
  - `gain`
  - `tremolo` (a sine LFO)
  - `biquad8` (an 8-stage stereo TDF-II cascade)
  - `delay` (1 s, feedback, interpolated)
  - `faulty`, where `p1[0]` picks the fault: `unreachable`, a NaN, `memory.grow`, an endless loop, or a sample of 1000
- **Host stand-in** (`host/src/lib.rs`, 1.2 KB): owns 32 slots of L/R buffers and parameter blocks in its own memory
  and calls `myco_ext.process(handle, l, r, frames, p0, p1, flags)` per slot, as the core's chains would. It keeps a
  quantum counter, a fault counter and an FNV hash of every output sample.
- **Glue** (`glue.js`): resolves the handle, copies in, sets fuel, calls the plugin inside `try`, checks the memory
  buffer's identity (growth), scans the output (non-finite or |x| > 64), and copies out. On a fault it returns −1
  without copying, so the host's buffers still hold the dry input: pass-through costs nothing. A later `recover()`
  plays the part of `onmessage`: it re-instantiates the module after a trap or growth, and destroys and re-creates the
  instance after a NaN or range fault. Five copy and scan strategies, described with the results.
- **Fuel pass** (`fuel.mjs`): a fork of the decoder and segmenter in `tools/audio-bench/meter.mjs`. That file exports
  only `meter`, so it was forked rather than edited. Every straight-line segment subtracts its instruction count from
  an exported global `__fuel` (i32 or i64). The modes and check forms:

  | Option | Checks |
  |---|---|
  | `segment` | every segment |
  | `loop` | only function entries and loop headers (decrements stay per segment, so counts stay exact) |
  | `count` | none; the meter's own increment, for comparison |
  | check form `if` | `global.get; const 0; lt_s; if unreachable end` (the record's form) |
  | check form `load` | `i32.load8_u` from address `fuel >> 31`: 0 while fuel ≥ 0, 0xFFFFFFFF once negative, which is out of bounds and traps. No branch |

- **Helpers** (`genwasm.js`, hand-assembled):
  - `scanModule()` (182 B) imports the plugin's memory and exports `scan(io, frames)` as a SIMD compare-and-mask.
  - `multiMemoryModule()` (315 B) imports both memories and exports `pre` and `post`, which move the block with
    `memory.copy` between memories and scan it.
  - `largeModule()` makes a synthetic ~100 KB DSP-shaped module (and a 9 MB one).
- **Drivers**: `build.mjs` (cargo +1.99.1 → `wasm/`), `run.mjs` (Node, then each Playwright browser),
  `page.js` and `processor.js` (the scratch page and its worklet), `summarize.mjs`.

## 1. Glue cost

Per call, from host wasm through the import and the glue into the plugin and back. `host_calls(n)` makes only the n
import calls. Columns are 1 / 8 / 32 instances per quantum; plugin kind `null`, so the plugin's own work is ≈ 10 ns.
All figures in ns.

| Strategy | Node V8 12.4 | Chromium 153 main | Chromium 153 worklet |
|---|---|---|---|
| empty wasm→JS import (reference) | 10 / 8 / 8 | 13 / 10 / 10 | 13 / 17 / 10 |
| `loop`: JS index loops for copies and scan | 1085 / 1140 / 1148 | 840 / 1138 / 908 | 835 / 1439 / 1435 |
| `set`: `TypedArray.set` from a fresh `subarray` per call (allocates) | 1014 / 1024 / 734 | 616 / 607 / 621 | — |
| `cached`: `set` from host views cached per slot; JS scan | 552 / 586 / 626 | 499 / 465 / 456 | 626 / 525 / 466 |
| **`wasmscan`**: `cached` copies; scan in the SIMD helper | **184 / 182 / 265** | **211 / 200 / 210** | **233 / 344 / 254** |
| `multimemory`: helper does copies and scan | 191 / 242 / 187 | 133 / 160 / 175 | 229 / 169 / 199 |
| `wasmscan` + i32 fuel (segment) | 232 / 199 / 220 | 235 / 231 / 232 | 249 / 307 / 402 |
| `wasmscan` + i64 fuel (a BigInt per call) | 231 / 224 / 242 | 252 / 252 / 264 | — |

- With real plugins the glue's share stays the same, and the plugin's own time adds to it. For gain at unity, under
  `wasmscan` in Node, the call costs 336 ns in total, of which the plugin is 188 ns. For the tremolo it's 1.5 µs, of
  which the plugin is 1.3 µs. The per-quantum cost at 32 instances is 6.7–8.5 µs for `null` under `wasmscan` and
  47–58 µs for the tremolo: 0.23–2% of a 2.9 ms quantum.
- **Where the time goes** (Node microbenchmarks, scratch code not kept):
  - The JS scan of 256 floats takes 280–340 ns. It dominates the naive glue.
  - The six `TypedArray.set` copies take ≈ 200 ns.
  - My first SIMD scan used a NaN-propagating `f32x4.max` and cost **380 ns**, because that max is several machine
    instructions in a loop-carried chain. A compare (`|x| ≤ 64`, false for NaN) ANDed into a mask costs **37 ns**.
  - `memory.copy` costs ≈ 15–20 ns each in V8 (helper `pre` with four copies: 70 ns).
  - `memory.buffer` reads cost ≈ 15 ns. `try`/`catch` costs ≈ 0.
- `multimemory` is ≈ 30–70 ns cheaper than `wasmscan` in Chromium but not in Node, and it needs multi-memory. Both
  V8 builds validate it. Safari's support isn't known here.
- Outliers (for example 1439 ns, 344 ns and 402 ns in the worklet) come from machine load; worklet timings use
  `Date.now` over ≥ 150 ms trials.

## 2. Fuel instrumentation overhead

These are direct calls to `process` (one 128-frame block), with the I/O refilled before every call so no signal decays
into subnormals; the refill's time is subtracted. All variants run interleaved, round by round, and each figure is the
median of 9 rounds. Each cell is the slowdown against the uninstrumented module.

**Node V8 12.4** (`b0.json`; `fuel-a` and `fuel-b` agree within ±5 points):

| Kind | instr/frame | plain | count | loop `if` | segment `if` | segment `if` i64 | loop `load` | segment `load` |
|---|---|---|---|---|---|---|---|---|
| gain | 30 | 155 ns | −1% | +17% | +30% | +45% | +11% | +27% |
| tremolo | 111 | 1267 ns | −1% | **+157%** | **+158%** | **+158%** | **−1%** | **−1%** |
| biquad8 | 502 | 7287 ns | +1% | 0% | +1% | +2% | +1% | 0% |
| delay | 186 | 1467 ns | +1% | +5% | +8% | +16% | +1% | +4% |

**Chromium 153**, main thread / worklet:

| Kind | plain | count | loop `if` | segment `if` | segment `if` i64 | loop `load` | segment `load` |
|---|---|---|---|---|---|---|---|
| gain | 160 / 161 ns | +8 / +9% | +22 / +20% | +17 / +13% | +13 / +13% | +14 / +14% | +16 / +18% |
| tremolo | 1414 / 1593 ns | −1 / +4% | −1 / +22% | −3 / −9% | 0 / −13% | +2 / 0% | +1 / −11% |
| biquad8 | 7497 / 7394 ns | −3 / −1% | −2 / −2% | −1 / +1% | −2 / −1% | −2 / −2% | −2 / −1% |
| delay | 1572 / 1581 ns | −1 / +3% | +4 / +4% | +1 / +16% | +2 / +4% | +3 / +1% | +2 / +4% |

- **The real number is 0–30%.** Kernels with a few hundred instructions per frame (biquads, delays) lose ≤ 8%. Only a
  4-instruction gain loop reaches 11–30%. The record's 20–50% guess is pessimistic for real DSP.
- **The cliff.** In V8 12.4, any `if … unreachable` in the tremolo's loop costs +157%, even in `loop` mode where the
  check runs once per loop iteration. The same decrements without a branch (the `count` and `load` forms) cost ≈ 0%.
  Chromium's V8 153 shows no cliff. So the cost of the branchy form depends on the engine version; the branch-free form
  is flat in both V8 builds tried.
- **i32 beats i64**: i64 is never cheaper in wasm, and setting an i64 global from JS takes a BigInt on every call.
- **Checks only at loop headers** gain little over checks in every segment once the check is branch-free (gain 11%
  against 27%; elsewhere within noise). They do shrink the module more: the test plugin goes from 5.4 KB to 7.6 KB in
  `loop` mode against 9.8 KB in `segment` mode.
- Instrumenting the shipped core in `segment` mode, for scale, takes it from 472 KB to 851 KB (23,650 segments).
- Instructions per frame, measured exactly with the count mode: one stereo biquad stage ≈ 63, the 8-stage cascade
  502, the tremolo 111, the delay 186, the gain 30. The record's default of 1,000 per frame fits a typical effect.
- Fuel starts at 0, so any call traps until the glue grants some. That is a good default; the glue gives `create` and
  `reset` a large grant.

## 3. Compiling inside the AudioWorklet

Chromium 153 only; JSC and SpiderMonkey are blocked.

| Probe in `AudioWorkletGlobalScope` | Result |
|---|---|
| `WebAssembly` present, `performance` absent | yes / absent (`Date.now` only), as 0157 found |
| sync `new WebAssembly.Module` + `Instance` from bytes | allowed at every size: plugin 0–1 ms, 100 KB 0 ms, core 472 KB 2 ms, decoder 1.1 MB 4 ms, **9 MB 17–21 ms** |
| the same 9 MB module on the **main thread** | **refused**: "WebAssembly.Compile is disallowed on the main thread, if the buffer size is larger than 8MB" |
| async `WebAssembly.compile` / `instantiate` | works; the promises resolve in the worklet. For 9 MB the call holds the thread **5–7 ms** and resolves after 20–23 ms |
| `node.port.postMessage({ module })` with a compiled `WebAssembly.Module` | **fails**: `messageerror` in the worklet, nothing delivered |
| `new AudioWorkletNode(…, { processorOptions: { module } })` | works: the processor instantiates it |
| `WebAssembly.compileStreaming` | defined, but useless without `fetch` or `Response` |

Compile, instantiate and first-call times (ms, mean of up to 200 compiles, with bytes made unique each time so no
cache answers):

| Module | Node compile / inst / first call | Chromium main | Chromium worklet |
|---|---|---|---|
| plugin 5.4 KB | 0.12 / 0.04 / 0.24 | 0.18 / 0.10 / 0.18 | 0.18 / 0.14 / 0.15 |
| plugin + fuel 9.8 KB | 0.14 / 0.03 / 0.23 | 0.19 / 0.06 / 0.27 | 0.15 / 0.08 / 0.23 |
| synthetic 100 KB | 0.38 / 0.04 / **1.32** | 0.51 / 0.14 / **1.15** | 0.48 / 0.14 / **1.13** |
| synthetic 100 KB + fuel | 0.51 / 0.04 / 1.09 | 0.58 / 0.21 / 1.24 | 0.47 / 0.13 / 1.17 |
| audio core 472 KB (compile only) | 1.8 | 3.3 | 3.5 |
| audio decoder 1.1 MB (compile only) | 3.9 | 8.5 | 7.2 |
| 100 KB, identical bytes again | 0.009 | 0.29 | 0.20 |

- The **first call** after instantiation costs more than the compile. V8 compiles functions lazily (Liftoff) on first
  use; for 100 KB of code that's about 1.1–1.3 ms on the audio thread.
- Recompiling identical bytes is nearly free: V8 caches native modules by their bytes.
- Fuel instrumentation adds about 4% of bytes to the 100 KB module and has no measurable effect on compile time.

## 4. Fault isolation

The setup: module A (segment fuel, budget 1,000 per frame) holds slots 0–3 (gain at unity) and slot 4 (`faulty`).
Module B (plain) holds slots 5–7 (tremolo at depth 0). Unity gain and depth 0 return their input's exact bits. Over 50
quanta, slot 4 faults at quantum 10, and `recover()` runs before quantum 11. The run is repeated for every glue
strategy, on Node, the Chromium main thread and the Chromium worklet: **35 runs**.

| Fault | Glue's reason | Host faults | Host quanta | Host hash = clean run | Instances re-created |
|---|---|---|---|---|---|
| `unreachable` | trap | 1 | 50 | **yes** (35/35) | 5 (the module) |
| NaN output | nonFinite | 1 | 50 | yes | 1 |
| `memory.grow(1)` in `process` | grow | 1 | 50 | yes | 5 (the module) |
| endless loop | trap (fuel) | 1 | 50 | yes | 5 (the module) |
| sample of 1000 | range | 1 | 50 | yes | 1 |

- **Without the glue's `try`** (a control run), the plugin's `RuntimeError: unreachable` unwinds through the host wasm.
  `host_quantum` aborts between its process loop and its bookkeeping (quanta 10, not 11). The core would be left
  mid-quantum, which is what 0157's hard rebuild exists for. The catch in the glue is required and enough.
- **How long a runaway holds the thread** before its fuel runs out, using the branch-free `load` check, per call:

  | Budget | Node | Chromium main | Chromium worklet |
  |---|---|---|---|
  | default, 1,000 instr/frame (128 k) | 0.04–0.10 ms | 0.10–0.21 ms | 0.07–0.13 ms |
  | maximum, 20,000 instr/frame (2.56 M) | 0.23–0.68 ms | 1.06–1.11 ms | 0.87–0.88 ms |

  So 32 instances running away in the same quantum at the maximum budget would hold the audio thread for ≈ 28–35 ms.
- **Recovery cost** (mean over 40 reps, or 400 in the worklet):

  | Step | Node | Chromium main | Chromium worklet |
  |---|---|---|---|
  | re-instantiate the module and re-create its 5 instances | 0.036–0.092 ms | 0.06–0.08 ms | 0.15–0.16 ms |
  | first quantum after that | 0.013–0.021 ms | 0.008–0.028 ms | 0.010–0.015 ms |
  | destroy and re-create one instance | 2.4–2.6 µs | 2.5–7.5 µs | 7.5–10 µs |

  The first quantum after re-instantiation is cheap because no compile happens: the same `WebAssembly.Module` is kept.
- **Memory growth** detaches every view on the plugin's buffer, so the glue treats it like a trap and re-instantiates.
  Every re-instantiation allocates a fresh `WebAssembly.Memory`. V8 reserves a large virtual range for each one, so
  repeated faults pile up reservations until GC; the record's "3 faults a second" rule bounds that.

## Blockers

- **WebKit (JavaScriptCore) and Firefox (SpiderMonkey) weren't measured.** Their Playwright builds aren't installed in
  `/opt/pw-browsers`, and downloading them failed: the network proxy refuses `playwright.download.prss.microsoft.com`
  (403). As a substitute I tried installing Bun (JSC) from npm into the worktree, and the session's permission check
  denied it. `run.mjs` already tries all three browsers, so on a machine with them installed,
  `node tools/spikes/fx-plugin/run.mjs` fills in the missing columns unchanged. Evidence from 0157's spike: WebKitGTK
  and Firefox 157 both instantiate wasm synchronously from bytes in `AudioWorkletGlobalScope`. Unknown: their fuel
  overhead, async compile in the worklet, whether a module posts over the port, and multi-memory (Safari probably
  lacks it).
- Shared, loaded VM with no audio device: no real-time glitch measurements, and some outliers in the glue tables.
- `Date.now` resolution in the worklet: sub-millisecond figures there are averages over long runs, and single fault
  quanta read as 0 or 1 ms.

## Recommended amendments to 0352

1. **The architecture holds.** The cost per call, fuel, sync compile in the worklet and fault isolation all work in
   V8 with room to spare. Measure JSC and SpiderMonkey with this spike before B4 merges, not before B1.
2. **§1, glue.**
   - State the per-call budget as ≈ 0.25 µs in V8, and require the scan to run in a **trusted helper module** per
     plugin module (ours, generated or embedded, importing that module's memory). It should be a SIMD
     compare-and-mask over `|x| ≤ 64`, not a NaN-propagating max.
   - Do the copies with `TypedArray.set` on host and plugin views cached per slot and pointer, rebuilt when either
     memory's buffer changes.
   - A JS scan loop alone costs more than the rest of the glue together (≈ 1 µs against ≈ 0.2 µs).
   - Multi-memory saves 30–70 ns in Chromium but isn't everywhere: leave it out of v1.
   - "Allocates nothing per call" holds for `cached`. The `subarray` form (`set`) allocates and is slower.
3. **§6, fuel.**
   - Use an **i32** global, not i64 (no BigInt on every call).
   - Decrement in every segment, so the profiler's counts stay exact, but **check only at function entries and loop
     headers**.
   - Make the check **branch-free**: `i32.load8_u` at `fuel >> 31`, which traps out of bounds. The ABI already
     requires an exported memory and the 64 MB cap keeps it far below 4 GiB.
   - The branchy `if unreachable` form showed a +157% engine-specific cliff, so B1's tests should keep a kernel like
     the tremolo as a regression guard.
   - Replace "expected 20–50%; if over 50% switch to loop headers" with the measured **0–30% (≤ 8% on biquad and
     delay kernels)**.
4. **§3, budgets.**
   - The per-instance maximum of 20,000 instructions per frame lets one runaway hold the thread for up to ≈ 1 ms, and
     32 of them for ≈ 30 ms. Add a **per-quantum aggregate fuel cap** across all plugin instances: the glue grants
     `min(instance budget × frames, quantum budget left)` and passes through the rest. Alternatively, lower the
     maximum to about 5,000.
   - Keep the default of 1,000, which covers the measured effects: one stereo biquad stage is ≈ 63 per frame.
5. **§8, add worklet compile rules.**
   - The main thread validates and instruments the module.
   - It **transfers the bytes** (an `ArrayBuffer`) on the port: Chromium can't deserialize a `WebAssembly.Module`
     posted on the node's port, and `processorOptions` only works when a node is created.
   - The worklet compiles with **async `WebAssembly.compile`**, which costs a 100 KB module ≈ 0.5 ms and holds the
     thread ≈ 5–7 ms for 9 MB. It falls back to sync `new WebAssembly.Module`, which is allowed in the worklet at any
     size; the 8 MB limit applies only to the main thread.
   - The worklet **keeps the `Module`** for every later re-instantiation and never recompiles on recovery.
   - It makes one **warm-up `create`, `process` and `destroy`** on silence before an instance goes live, because
     V8's lazy first-call compile costs ≈ 1.1–1.3 ms per 100 KB.
6. **§6, faults.**
   - Count a growth in `process` as a module fault (re-instantiate): its views are detached.
   - Note that each re-instantiation allocates a new memory, bounded by the 3-faults-a-second rule.
   - Re-creating an instance in place (destroy and create) assumes the plugin's allocator frees memory: this spike's
     bump allocator leaked on every reset. The SDK's `export_effects!` should ship a real allocator, and the guide
     should say that `create` may grow memory up to `memoryMB` and `process` never may.
7. **Build plan path:** the record names `docs/design/0352-audio-effect-plugins/spikes.md`; this report is at
   `docs/design/audio-studio/spikes/0352-b0.md` as briefed. Point the record there, or move the report.
8. **B1:** the forked `fuel.mjs` shows the meter's decoder carries over to fuel unchanged: one segmenter, three
   prefixes. Moving it into `src/engine/wasm/meter.js` with `count`, `fuel-loop` and `fuel-segment` modes is a small
   step. A unit test should check that `count` mode's output is bit-identical to today's `meter()`.

## Reproducing

```sh
node tools/spikes/fx-plugin/build.mjs                       # needs cargo +1.99.1 and wasm32-unknown-unknown
node tools/spikes/fx-plugin/run.mjs --node-only             # Node only (≈ 6 min)
E2E_PORT=4391 node tools/spikes/fx-plugin/run.mjs --out tools/spikes/fx-plugin/results/b0.json   # + Playwright browsers
node tools/spikes/fx-plugin/summarize.mjs tools/spikes/fx-plugin/results/b0.json
```

`--only glue,fuel,compile,faults` limits the Node part. Playwright is resolved from the repository's `node_modules`,
and no e2e spec or config is touched.
