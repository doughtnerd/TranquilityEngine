# Debug-link pairing and the audio topic: milestones and waves

## 1. Purpose and authority

This plan builds [ADR 0403](../decisions/0403-debug-link-pairing-reaches-every-native-and-browser-endpoint-on-one-network.md)
(either side listens, short-code pairing, mDNS, a `webrtc` transport, rendezvous) and the audio debug-link topic the
Audio Studio needs to record takes from running games and the editor (0376's "audio topics" gap, 0348's open question).

There is no separate design or task table: **ADR 0403, 0376 and 0348 own behaviour**; this plan owns the task table
below (IDs, estimates, dependencies, acceptance), order, file ownership and gates. Where this plan names files beyond
0403's **Code** list, the plan's list is the build's (accepted records aren't rewritten; the implementation-status row
records the final files). Where the plan has to settle something 0403 leaves unsaid, it says so (§11, "plan
decisions") and the owner confirms. Companion files: [tree](2026-11-debug-link-pairing-tree.md),
[ground rules](2026-11-debug-link-pairing-ground-rules.md), [handoff](2026-11-debug-link-pairing-handoff.md).
An independent review (2026-11-23, 13 findings) is folded in; §12 lists each finding and its fix.

## 2. State at planning (checked 2026-11-23)

- Base: `master` at `4caf082db` (animation merge, PR 189). Planning branch `claude/live-game-connection-2fad35`.
- 0403 Accepted; 0376 partly superseded by it; 0379 amended by it. Highest record 0403.
- **Exists:** `src/engine/debugLink/` (`session.ts` build side, `client.ts` tool side `DebugLinkListener`/`DebugLinkPeer`,
  `host.ts` connects out and reconnects every 2 s, `protocol.ts` `DEBUG_LINK_VERSION = 1`, `DebugHello { name, platform,
  topics }`, `topics.ts` registry, `config.ts` parses `debug.link`/`debug.webrtc`); `src/editor/debugLink/` (listener,
  accept prompt, builds menu, settings, `tauriListener.ts`); `native/ws-listener` (tungstenite, 10 cargo tests);
  `src-tauri/src/debug_link.rs` (three commands). Session and peer take a `TransportConnection`, but **the session's
  first message assumes the build role**: the build sends `hello` the moment the session is built, and the tool has no
  first message of its own.
- **Samples travel on the unreliable channel** (`session.ts`, `send("unreliable", …sample…)`); a lost capture segment
  ends a live follow (`liveLost`).
- **The release-export rule** (`vite.shared.ts` `DEBUG_LINK`) matches files *directly* in `src/engine/debugLink/` and
  plugin `runtime/**/debugLink/` folders. Subfolders (`pairing/`, `rendezvous/`), `net/transport/webrtc.ts`, a player
  overlay and the listener transport are **not** covered today.
- Only the animation topic is registered (`src/plugins/animation/runtime/features/debug/register.ts`). Audio has none.
- `src-studio-tauri/` has no debug-link commands; `src/studio/main.tsx` starts no link.
- Desktop game apps are generated as text by `src/export/desktop.ts` (it already injects `--debug-link`); they hold no
  listener. `webBuild.ts` writes only `debug: { link }`.
- `serve.mjs` (generated by `webBuild.ts`) is dependency-free and **listens on `127.0.0.1` only**; the Vite dev server
  listens on localhost. Neither is reachable from another machine today.
- The Node WebSocket server (`src/server/websocketServer.ts`) uses the `ws` package (0035).
- Takes: `Audio.take` (`src/plugins/audio/runtime/capture/take.ts`) with `start/stop/save`; live capture reaches the
  Profiler through `LiveHost`/`LiveRecording` (`src/plugins/audio/editor/mix/liveFollow.ts`).
- **Android games work today through the Tauri CLI** (owner, 2026-11-23: tested): a `--target desktop` export's Tauri
  project is built for Android with `tauri android init`/`build` or Android Studio. The exporter's own
  `--target android` (0155) isn't built (`src/export/node.ts`), so `gen/android/` is the user's, not exporter-patched.
  Consequence: Android games get the listener through the same vendored crates as desktop (U6); anything Android
  needs in `gen/android/` (cleartext to private addresses, the multicast lock) is written as instructions in D3, not
  generated. There is no Android build of the Studio (`src-studio-tauri` has no `gen/android/`) and no record for
  one (O1).
- No Tauri app is run by any automated test; 0379's listener is "not verified in a running app".

## 3. What shippable means

Every merge to the integration branch passes `npm run typecheck`, `npm test`, `npm run build`, `npm run test:e2e`,
and `cargo test` in each touched crate. Between merges:
- the existing direction (tool listens, build connects with `--debug-link`/`debug.link`, the accept prompt for
  non-local builds) keeps working unchanged;
- a **release export holds none of the new code**: L0 widens the `DEBUG_LINK` rule before any new file exists, with a
  test that every new module is in `files.json`'s `debug` list;
- build-side listening is **opt-in** per export (`debug.listen`, LAN only with `debug.lan`); there is no default to flip.
  The protocol version moves to 2 in L1; both ends are always built together and v1 peers are refused with a message.

**Plan decisions** (0403 is silent; the owner confirms):
- A build connecting to a tool takes the tool's code by launch flag or query (`--debug-code`, `?debug-code=`); the game
  has no code entry field. Without a code, 0376's accept prompt applies (O6).
- `debug.webrtc` (0333's lane beside a WebSocket) stays as it is: still useful for samples on a WebSocket link; 0403
  only stops relying on it for remote devices.
- Bulk transfers use 64 KiB messages on every transport (O5).

**Owner items:**
- **O1** The Studio on Android: no Android build of the Studio exists, and 0341 doesn't cover one. Android games are
  in scope (D3); the three Android Studio pairs wait for a record of their own. **Decided (owner, 2026-11-23): later,
  outside this plan.**
- **O2** How a debug game app gets the listener. A desktop export already writes a Tauri project and compiles it with
  the *developer's* cargo (`tauri build`, `node.ts`; without cargo it writes the project only), copying
  `src-tauri/src/gamepad.rs` in as text (0335). Players get a compiled installer and never need Rust. The listener
  would go in the same way, only in exports with debugging on: `native/ws-listener` and `native/debug-link-tauri`
  sources written into `<out>/src-tauri/` as path dependencies. Alternatives: publish the two crates to crates.io (the
  generated `Cargo.toml` names a version), or a prebuilt debug shell binary per platform (removes the developer's
  Rust need for debug builds, but is a new record and CI). **Decided (owner, 2026-11-23): write the sources in, as
  with `gamepad.rs`.**
- **O3** Who hosts a public rendezvous (0403 open question). **Decided (owner, 2026-11-23): no public rendezvous.** R3

  The owner confirmed (2026-11-23) that M2 stays as planned: without a rendezvous, browser ↔ browser pairs and
  https pages could only exchange takes as files.
- **O4** Hardware. **Decided (owner, 2026-11-23): desktop, laptop, Android phone.**
- **O5** 64 KiB bulk messages. **Decided (owner, 2026-11-23):** 64 KiB is the existing ceiling of the WebRTC lane
  (`websocket.ts`: `maxDatagramBytes` up to 65,536, a 64 KiB unreliable backlog); A2 cuts take uploads to it and R2

- **O7** **Where the rendezvous is.** A room code holds a room and a token, not a server, so two pages served by
